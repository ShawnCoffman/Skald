# Build Plan — Open-Source Windows Performance Forensics Tool

## Project Goal

Build a lightweight, open-source Windows application that answers a question Task Manager usually does not:

> **Why is this computer slow, hot, using too much power, draining its battery, or behaving differently than normal?**

The application should combine live system monitoring, process correlation, historical recording, automated bottleneck detection, and replayable diagnostic sessions.

This is not intended to be another generic Task Manager clone.

The focus is:

> **Observe → correlate → explain → record → replay**

The application should be useful for both technical users and enterprise support teams troubleshooting vague tickets such as:

- "My computer is slow."
- "My laptop battery only lasts six hours now."
- "The fan runs constantly."
- "Everything freezes randomly."
- "The disk is at 100%."
- "Task Manager says CPU isn't maxed out, but the machine still feels slow."
- "It was fine yesterday."

---

# 1. Core Diagnostic Philosophy

Organize system performance around simple questions rather than hundreds of raw counters.

### CPU — Who is computing?

Determine:

- Which processes are consuming CPU.
- Per-process CPU utilization.
- Per-core / logical processor utilization.
- Whether one core is saturated.
- CPU frequency.
- Effective clock where available.
- Kernel vs user CPU time.
- CPU temperature where available.
- CPU package power where available.
- Thermal throttling.
- Power limiting.
- CPU saturation duration.

The tool should distinguish situations such as:

> CPU is highly utilized and operating normally.

from:

> CPU is highly utilized but being power-limited.

from:

> Total CPU utilization is only 18%, but one logical processor has been saturated for four minutes.

---

# 2. Memory — Where is the pressure?

Collect:

- Physical RAM installed.
- Physical RAM used.
- Available memory.
- Cached memory.
- Standby memory.
- Modified memory.
- Memory compression.
- Commit charge.
- Commit limit.
- Commit percentage.
- Pagefile usage.
- Page reads/writes.
- Hard faults/sec.
- Per-process working set.
- Per-process private bytes.
- Per-process commit.

Do not treat "90% RAM used" alone as a problem.

The diagnostic engine should differentiate:

### Healthy high utilization

> 88% of RAM is occupied, but significant standby/cache memory is reclaimable and paging is minimal.

### Actual memory pressure

> Physical memory availability is low, commit utilization is high, and sustained hard paging is occurring.

### Process growth

> msedge.exe increased from 2.1 GB to 8.4 GB during the session and is the largest contributor to memory pressure.

---

# 3. Disk Activity — Where are we waiting?

Monitor each physical disk and logical volume.

Collect:

- Read throughput.
- Write throughput.
- IOPS.
- Active time.
- Average read latency.
- Average write latency.
- Queue depth.
- Outstanding I/O.
- Disk health where available.
- Process-level disk I/O.
- File-level activity when practical.
- Storage type.
- Bus/interface.
- Model.
- Firmware.
- Capacity.

Diagnose the difference between:

### Bandwidth saturation

> Disk is processing 5.8 GB/s with low latency.

and:

### Latency saturation

> Disk is at 100% active time while processing only 22 MB/s, with 140 ms average latency and a queue depth of 12.

The second condition should be highlighted as a likely performance issue.

---

# 4. Disk Space — Where did the bits go?

Provide a storage-capacity analysis separate from disk performance.

Display:

- Total capacity.
- Free space.
- Used space.
- Percentage free.
- Largest directories.
- Largest files.
- User profile usage.
- Temp/cache usage.
- Windows Update/cache usage.
- Application usage.
- Optional previous scan comparison.

Example:

> C: has 17.4 GB free of 476 GB.

Then:

> Largest consumers:
>
> Users — 184 GB  
> Program Files — 91 GB  
> Windows — 48 GB  
> ProgramData — 37 GB

Allow drilling down into directories.

Avoid automatically deleting anything.

---

# 5. GPU — Who is rendering/accelerating?

Collect where supported:

- GPU utilization.
- GPU engine utilization.
- Dedicated VRAM used.
- Shared GPU memory.
- GPU temperature.
- GPU power.
- GPU clock.
- Video decode utilization.
- Video encode utilization.
- Compute utilization.
- Per-process GPU usage.

Especially important on laptops:

Determine whether a discrete GPU is awake when it should not be.

Example:

> NVIDIA discrete GPU remained active for 84% of this session despite no 3D workload.

That should become a battery/power diagnostic event.

# 7. Power — Where is the energy going?

This should be a major feature.

Collect where supported:

- AC/battery state.
- Battery percentage.
- Battery design capacity.
- Full-charge capacity.
- Battery health percentage.
- Charge/discharge rate.
- Battery voltage.
- Estimated power draw.
- CPU package power.
- GPU power.
- Platform power information.
- Power plan.
- Windows power mode.
- Sleep-state behavior.
- Modern Standby information where relevant.

Unsupported sensors must be represented as:

> Unavailable

Never infer a numeric value and display it as measured data.

# 8. Battery Analysis

Battery health and battery consumption must be treated as different concepts.

Example:

> Battery health: 99%

does not imply:

> Battery runtime is normal.

The application should analyze:

### Battery capacity

- Design capacity.
- Full-charge capacity.
- Cycle count if available.
- Health percentage.

### Battery consumption

- Current discharge rate.
- Average discharge rate.
- Peak discharge.
- Discharge over recording period.
- Estimated runtime at current workload.

### Correlated activity

Look for correlations between discharge rate and:

- CPU usage.
- CPU package power.
- GPU activity.
- dGPU wake state.
- Display configuration.
- Display refresh rate.
- brightness where accessible.
- Wi-Fi activity.
- storage activity.
- background processes.
- sync applications.
- antivirus activity.
- webcam use.
- external USB devices.

The software must clearly distinguish measured attribution from correlation.

Do not claim:

> Chrome used exactly 3.8 watts

unless Windows/hardware provides reliable direct attribution.

Instead say:

> Increased battery discharge coincides with sustained Chrome CPU activity and discrete GPU activation.

---

# 9. Thermals — Why can't the machine go faster?

Monitor:

- CPU temperature.
- GPU temperature.
- thermal zones.
- frequency changes.
- throttling indicators.
- processor performance limits.
- platform thermal events.

Detect conditions such as:

### Thermal throttling

> CPU temperature repeatedly reached its thermal limit and effective clock decreased under sustained load.

### Power limiting

> CPU remained below thermal limits but reached its configured sustained power ceiling.

### No hardware limitation

> CPU utilization is high, but no thermal or power limiting was detected.

# 12. Explainable Diagnostics

Every diagnosis must be explainable.

Example:

```text
Memory Pressure: HIGH

Physical RAM used:       94%
Commit used:             89%
Available RAM:           1.2 GB
Hard faults/sec:         1,460
Page reads:              188 MB/s
Duration:                134 sec

Triggers:
✓ Physical memory > 90%
✓ Available RAM below configured threshold
✓ Sustained paging detected
✓ Condition persisted longer than 30 sec
```

Avoid black-box scores such as:

> PC Health Score: 62

unless the score can be decomposed into explicit, understandable rules.

Provide at least two modes.

- process snapshots

- memory

- GPU

For difficult performance investigations.

# 27. Collector Interface

Collectors should be modular.

Conceptually:

```csharp
public interface IMetricCollector
{
    string Name { get; }

    bool IsSupported { get; }

    Task InitializeAsync();

    Task<MetricSample> SampleAsync(
        CancellationToken cancellationToken);

    Task ShutdownAsync();
}
```

Each collector should report capability status.

Example:

```text
CPU utilization       Supported
CPU frequency         Supported
CPU temperature       Unsupported
CPU package power     Supported
CPU limit reasons     Supported
```

This keeps unsupported hardware from breaking the application.

# 30. Permissions

Normal monitoring should run without administrator rights whenever possible.

Only request elevation for functionality that genuinely requires it.

Do not launch the entire application elevated by default.

Display capability limitations rather than failing.

Example:

> Detailed storage health requires administrator privileges.

Then allow:

> **Enable Elevated Diagnostics**

if needed.

---

# 31. Safety

Version 1 should be primarily read-only.

Do not include:

- process termination
- driver changes
- registry changes
- service modifications
- power-plan changes
- disk cleanup
- application removal

until the monitoring and diagnostic platform is stable.

The application explains problems before attempting to fix them.

# 32. Diagnostic Rules Engine

Keep diagnostic rules separate from collectors.

Example:

```text

    ↓

    ↓

    ↓
```

```text
MemoryPressureHigh

AND
```

- trigger conditions
- supporting metrics
- start time
- end time
- severity
- contributing processes

The monitoring application itself must not become the performance problem.

Initial goals:

<1% average if practical.

<2%.

### Memory

### Disk writes

Avoid writing every metric synchronously every second.

### Memory

- gradual allocation

### Disk

### Network

- sustained transfer

# 53. Guiding Rule

Whenever considering adding another counter, ask:

> **What troubleshooting question does this measurement answer?**

If there is no good answer, do not put it on the main interface.

Raw telemetry may still be available under an advanced view, but the main application should remain focused on explaining system behavior.

---

# Final Product Definition

This application is:

> **An open-source Windows performance forensic tool that combines live monitoring, subsystem pressure analysis, process correlation, battery and power diagnostics, and a replayable flight recorder to explain why a Windows computer is performing poorly.**

It is **not** merely a Task Manager replacement.

Its defining feature should be:

> **Don't just show me what the computer is doing. Show me why it's happening — and let me replay it after the problem is gone.**

Implemented: grouped subsystem navigation; dedicated CPU and Memory views; compact overview hardware strip; contributor presets; process column presets with frozen identity columns; Power, Clocks & Thermals view; identified sensor records; NVIDIA clock telemetry; optional existing hardware-sensor WMI providers; timestamp-based power history; combined recording/replay navigation and shared chart controls; 60-second historical analysis with 30-second sustained-condition rules.

Still planned: direct CPU hardware-sensor access without an external provider, effective-clock collection, measured thermal/power-limit indicators, commit/paging and storage-latency counters, SQLite session writing, and full replay of every live subsystem view. The current portable recording format remains compressed JSON. Unsupported measurements remain explicitly unavailable.
